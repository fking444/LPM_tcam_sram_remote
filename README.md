# LPM 表项管理（TCAM + SRAM）

三层转发查表用 LPM。硬件上是两级存储：TCAM 存 key 和 mask 做并行比对，SRAM 存下一跳、
出接口这类 payload。TCAM 命中哪一行，就按行号去 SRAM 对应位置取数据。

一条路由不好放。IPv6 /128 的 key 加 mask 是 256 bit，TCAM 行宽没这么宽，得拆成几行存。
拆几行、续行怎么和首行绑定、删掉之后留的空洞怎么复用，这几件事互相影响。分配算得不好，
实际能装的路由数会远低于标称容量。

这个仓库是那套分配逻辑的主机侧模型，加一套验证它的扫描测试。不依赖厂商 SDK，Python 3.9
以上直接跑。

![查表流水](docs/images/lookup-pipeline.svg)

## 表结构

路由统一成 `(key, key_len, payload)`。IPv4 左移 96 位对齐到 128 位空间，和 IPv6 共用一张表：

```
IPv4 10.1.2.0/24    key = 0x0a010200 << 96   key_len = 24
IPv6 2001:db8::/64  key = 2001:0db8::0000    key_len = 64
```

远端模式的差别只在 payload，key 部分不动，匹配语义不受影响。

一条表项占多少行：

```
rows = ceil(round_up(key_len, 8) / cell_bits) + ceil(payload_bits / cell_bits)
```

`key_len` 要先向上取整到 8 bit。不取整的话短前缀在行内的 mask 表达不出来。

## 多行拼接

一条表项占多行时，只有第一行是有效行（`VLD=1`），后面几行 `VLD=0`，靠首行的 `span`
字段带出来。匹配器只在 `VLD=1` 的行里挑最长前缀，命中后按 `span` 检查后续行是否完整。

这样不会出现只对上后半段的误命中。优先级比较只在表项数量上做，不随行数增长。

## cell 位宽

位宽不能随便定。6000 条混合前缀（60% IPv4 /8~/24，40% IPv6 /32~/128），同样的行预算，
带 40% 插删，三档实测：

| cell 位宽 | 平均 span | 位利用率 | 能装下条目 | 碎片挡住 |
|---|---|---|---|---|
| 32 bit | 2.71 | 0.851 | 2117 | 1490 |
| 48 bit | 2.44 | 0.625 | 2353 | 1429 |
| 64 bit | 2.22 | 0.515 | 2551 | 1394 |

窄位宽位利用率高，但 span 大，需要的连续空间长，碎片一多就插不进去。宽位宽能塞更多条目，
代价是填充位多：IPv4 /8 放在 64 bit 行里只用了 8 位，剩下 56 位是空的。

选哪个取决于硬件先耗尽行数还是先耗尽总位数。

## 删除与压缩

表项变长，删一条留一个洞。洞的大小不规整，大表项塞不进去。

删除只打标记，碎片率超过阈值再整段压缩。阈值取 0.25 左右：低于这个值零星空洞还能被
小表项用掉；高于它，连续大块基本不会自然形成，会出现空闲总量够但插不进一条 /128 的情况。

分配用 best-fit，在空闲区里找尺寸最接近的洞。

## 验证

正常流量碰不到表项的边界。错误集中在前缀长度 0/1/31/32/127/128、相邻前缀重叠、
本地刚溢出到远端的那一条、以及压缩进行到一半的中间态。

所以不做典型用例，按前缀长度分层做地址扫描。每层四个探测点：网络地址本身、加一、减一、
以及掩码外翻转一位。

期望值取自一份独立写的朴素最长匹配，把前缀全过一遍取最长的。O(n) 慢，但语义不会错。
两份对不上就是模型错了。

失败输出带前缀长度、探测类型、地址、期望与实际、锚行行号和 span。

```
python tests/test_sweep.py
python tests/test_sweep.py --len 127
```

## 范围

模型是行为级的，不是 RTL，没有时序。容量参数是抽象值，不指任何具体芯片。
真实项目的芯片规格、寄存器映射、编码格式属于受限信息，没有放进来。
