# LPM 表项管理（TCAM + SRAM）

TCAM 存 key 和 mask，SRAM 按行号存 payload。IPv6 /128 的 key 加 mask 共 256 bit，超过单行位宽，一条表项要跨几行。

跨行之后有三件事要一起处理：拆几行、续行怎么跟首行绑、删掉之后留下的洞怎么补。分配算得不好，实际能装的路由数会远低于标称容量。

跑地址扫描用 `python tests/test_sweep.py`。这套代码不依赖厂商 SDK，有 Python 3.9 和标准库就能跑起来。

## 表结构

路由统一成 `(key, key_len, payload)`。IPv4 左移 96 位对齐到 128 位空间，和 IPv6 共用一张表：

```
IPv4 10.1.2.0/24    key = 0x0a010200 << 96   key_len = 24
IPv6 2001:db8::/64  key = 2001:0db8::0000    key_len = 64
```

远端模式的差别只在 payload，key 和匹配语义都不动。

一条表项占多少行：

```
rows = ceil(round_up(key_len, 8) / cell_bits) + ceil(payload_bits / cell_bits)
```

`key_len` 按 8 bit 向上取整，否则短前缀的 mask 在行内表达不出来。

## 多行拼接

一条表项占多行时，只有首行 `VLD=1`，其余行 `VLD=0`，靠首行的 `span` 字段带出来。匹配器只在 `VLD=1` 的行里挑最长前缀，命中后按 `span` 检查后续行是否完整。

只对上后半段的行不会被当成命中；优先级按表项比，跟行数没有关系。

## cell 位宽

下面这组数据来自 6000 条混合前缀（60% IPv4 /8~/24，40% IPv6 /32~/128），行预算固定，中间掺了 40% 的插入和删除，三档位宽各跑一遍：

| cell 位宽 | 平均 span | 位利用率 | 能装下条目 | 碎片挡住 |
|---|---|---|---|---|
| 32 bit | 2.71 | 0.851 | 2117 | 1490 |
| 48 bit | 2.44 | 0.625 | 2353 | 1429 |
| 64 bit | 2.22 | 0.515 | 2551 | 1394 |

位宽窄的时候位利用率高，但每条表项占的行多，需要的连续空间长，碎片一多就插不进去。位宽放宽了能塞下更多条目，代价是填充位变多：IPv4 /8 放进 64 bit 行只占 8 位，剩下 56 位空着。

到底选哪种，要看硬件是先耗尽行数，还是先耗尽总位数。

## 删除与压缩

表项长度不一样，删掉一条就在表里留下一个洞。洞的大小跟着被删的那条走，尺寸不规整，之后的长表项经常塞不进去。

删除的时候只给这几行置个标记位，等碎片率超过阈值再做一次整段压缩。阈值取 0.25：低于这个值，零星空洞还能被短表项吃掉；高于它，连续的大块基本不会自然形成，会出现空闲总量够、却插不进一条 /128 的情况。

具体分配走 best-fit，在空闲区里挑一个尺寸最接近的洞。

## 验证

错误集中在几个窄带上：前缀长度 0/1/31/32/127/128、相邻前缀重叠、本地刚溢出到远端的那一条、压缩进行到一半的中间态。常规流量碰不到这些地方。

挑几条典型路由来测，上面这些位置基本覆盖不到，所以改成按前缀长度分层做地址扫描。每层取四个探测点：网络地址本身、加一、减一，以及掩码外面翻转一位。

期望值来自另一份独立写的朴素最长匹配，把所有前缀遍历一遍取最长的那条。这样跑得慢，但跟被测实现没有共用一行代码，两边对不上就说明模型错了。

失败的时候会把前缀长度、探测类型、地址、期望与实际、锚行行号和 span 一起打出来。

```
python tests/test_sweep.py
python tests/test_sweep.py --len 127
```
