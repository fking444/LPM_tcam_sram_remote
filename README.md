# LPM 表项管理（TCAM + SRAM）

范围：LPM 表项在 TCAM + SRAM 上的分配模型，与对应的地址扫描验证。  
存储：TCAM 存 key 和 mask，行内并行比对；SRAM 按行号存 payload，即下一跳、出接口。  
寻址：TCAM 命中行号 → SRAM 同行号取数据。  
行宽：IPv6 /128 的 key + mask 共 256 bit，超过单行位宽，表项跨行存放。  
约束：跨几行、续行与首行如何绑定、删除后空洞如何复用，三者互相牵制。分配不当，实际可装路由数低于标称容量。  
运行：Python 3.9+，仅标准库，不依赖厂商 SDK。

![查表流水](docs/images/lookup-pipeline.svg)

## 表结构

路由统一为 `(key, key_len, payload)`。IPv4 左移 96 位对齐到 128 位空间，与 IPv6 共用一张表：

```
IPv4 10.1.2.0/24    key = 0x0a010200 << 96   key_len = 24
IPv6 2001:db8::/64  key = 2001:0db8::0000    key_len = 64
```

远端模式只改 payload，key 不变，匹配语义不受影响。

一条表项占用的行数：

```
rows = ceil(round_up(key_len, 8) / cell_bits) + ceil(payload_bits / cell_bits)
```

`key_len` 向上取整到 8 bit。不取整时，短前缀的 mask 在行内无法表达。

## 多行拼接

一条表项占多行时，只有首行 `VLD=1`，其余行 `VLD=0`，由首行 `span` 字段带出。匹配器只在 `VLD=1` 的行里取最长前缀，命中后按 `span` 校验后续行完整。

部分命中不成立。优先级比较在表项维度进行，行数不影响比较结果。

## cell 位宽

6000 条混合前缀（60% IPv4 /8~/24，40% IPv6 /32~/128），固定行预算，40% 插删，三档实测：

| cell 位宽 | 平均 span | 位利用率 | 能装下条目 | 碎片挡住 |
|---|---|---|---|---|
| 32 bit | 2.71 | 0.851 | 2117 | 1490 |
| 48 bit | 2.44 | 0.625 | 2353 | 1429 |
| 64 bit | 2.22 | 0.515 | 2551 | 1394 |

窄位宽位利用率高，span 大，要求的连续空间长，碎片一多即插入失败。宽位宽容纳条目多，填充位也多：IPv4 /8 放进 64 bit 行只占 8 位，其余 56 位为空。

选型依据是硬件先耗尽行数，还是先耗尽总位数。

## 删除与压缩

表项长度不等，删除留洞。洞尺寸不规整，长表项插不进去。

删除只置标记位，碎片率超阈值整段压缩。阈值取 0.25：低于该值零星空洞可被短表项消耗；高于该值连续大块不再自然形成，出现空闲总量足够但插不进一条 /128 的情形。

分配用 best-fit：空闲区里取尺寸最接近的洞。

## 验证

错误集中在前缀长度 0/1/31/32/127/128、相邻前缀重叠、本地溢出到远端的那一条、压缩中间态。常规流量不落在这些位置上。

按前缀长度分层做地址扫描，不用典型用例。每层四个探测点：网络地址、加一、减一、掩码外翻转一位。

期望值取自独立实现的朴素最长匹配：遍历全部前缀取最长。O(n)，慢，不含被测实现的假设。两份不一致即模型出错。

失败输出为前缀长度、探测类型、地址、期望与实际、锚行行号、span。

```
python tests/test_sweep.py
python tests/test_sweep.py --len 127
```
