# LPM on TCAM + SRAM — 表项下发与资源编排

三层交换机的最长前缀匹配（LPM）转发，在 **TCAM 存 key/掩码 + SRAM 存 payload** 的混合存储上实现时，真正的难点不是查找算法，而是**资源编排**：TCAM 行数、SRAM 的 cell 深度、cell 位宽三者互相牵制，任何一项分配失当都会让可承载的路由数远低于硬件标称容量。

这个仓库是上述问题的**行为级模拟器**与**验证方法**整理。代码不依赖任何厂商 SDK，用合成数据复现约束下的分配与查找逻辑，可以直接跑。

---

## 1. 问题

三层转发表要同时支撑 IPv4 与 IPv6。IPv6 前缀最长 128 bit，一条路由的 key + mask 就是 256 bit；而 TCAM 的最小寻址粒度是固定宽度的行（cell）。于是产生四个互相纠缠的约束：

| 约束 | 表现 |
|---|---|
| **cell 位宽 vs 条目数** | 位宽越大，单条路由占的行越少，但短前缀（如 IPv4 /8）会浪费大量位；位宽越小，灵活但一条路由要跨多行拼接 |
| **跨 cell 拼接** | 一个逻辑表项被切成多行后，匹配时必须保证这些行被同一优先级命中，否则会出现「部分命中」的脏结果 |
| **多条匹配行合成一个表项** | 长前缀 + 附属属性需要多行同时参与，形成 multi-row entry |
| **删除与空洞** | 表项是变长的，删除后留下不连续空洞，不压缩则容量快速碎片化 |

再加上 IPv4/IPv6 双栈和「远端」（remote）模式——下一跳不在本机直连域时，payload 结构不同——寻址方式必须统一，否则同一张表里两套编码。

## 2. 思路

整体流水长这样：

![LPM 查表流水](docs/images/lookup-pipeline.svg)

把「一条路由」和「它占的物理行」彻底解耦，中间加一层**分配器**：

```
路由前缀  ──►  逻辑表项 (key, mask, payload)  ──►  物理行分配  ──►  TCAM 行 + SRAM cell
                  │                                      │
                  │                                      └─ 位宽策略 / 空洞复用 / 拼接约束
                  └─ 去重、优先级、双栈归一
```

关键取舍写在 `docs/architecture.md`，核心是三点：

1. **位宽是三方折中，没有最优解**。窄位宽位利用率高、单条占位少，但平均 span 大，需要更长的连续空间，一旦碎片化就更容易被挡住；宽位宽能在同样的行预算里塞下更多条目，代价是一半以上的位是填充。跑 `src/cell_allocator.py` 实测三档：32 bit 的 `bit_util` 0.85 但 `blocked` 1490 条最多，64 bit 只装得下 0.52 的利用率却能多塞 434 条。**取哪个取决于你的瓶颈是总位数、行数，还是仲裁压力**——不是拍脑袋选个中间值。
2. **拼接用锚行**。跨 cell 的表项只有第一行带有效标志位，后续行靠行号偏移绑定，匹配器只需对锚行做优先级仲裁，避免部分命中。
3. **删除走标记 + 延迟压缩**。立即搬移会造成读写风暴，先打删除标记，当碎片率越过阈值再整段压缩。

## 3. 验证方法

硬件表项的 bug 极难在正常流量下暴露——大多数错误只在**边界地址**上才出现（前缀长度 0/1/31/32/127/128、相邻前缀重叠、远端模式边界）。所以验证不写"典型用例"，而是做**地址扫描**：按前缀长度分层，对每一层做全边界 + 随机采样，逐条比对「软件期望的命中结果」与「从表里读回的实际结果」。

细节见 `docs/test-method.md`，实现见 `tests/test_sweep.py`。扫描器能定位到具体是哪个前缀长度、哪种地址类型出的错，而不是笼统报「表项不符」。

## 5. 跑起来

只需要 Python 3.9+，无第三方依赖。

```bash
python tests/test_sweep.py          # 跑完整的地址扫描
python src/cell_allocator.py        # 看不同 cell 位宽下的占用对比
```

`cell_allocator.py` 直接运行时输出一组对照：6000 条混合前缀、同等的行预算、带 40% 插删 churn，在 32 / 48 / 64 bit 三档下的平均 span、位利用率，以及**明明有足够空闲行却因为不连续而插不进去**的条数——最后这个数才是碎片化的真实代价。

## 6. 范围说明

- 这里的代码是**行为级模型**，目的是验证分配与查找逻辑，不是可直接综合的 RTL，也不含任何硬件时序。
- 真实项目中的芯片规格、寄存器映射、编码格式属于受限信息，未包含在本仓库内。本文只保留架构思路与验证方法。
- 模拟器的容量参数是抽象值，用于演示策略差异，不代表任何具体芯片。
