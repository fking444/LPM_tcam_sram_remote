# 架构：两级存储与分配策略

## 1. 存储分层

```
                ┌──────────────────────────────────────────┐
   查找请求      │            LPM 查找流水                  │
   (dst addr) ──►│  key + mask 并行比对                      │
                └───────────────┬──────────────────────────┘
                                │ 命中的行号 (row index)
                                ▼
                ┌──────────────────────────┐   ┌─────────────────────────┐
                │   CAM 阵列（存 key/mask） │   │  SRAM 阵列（存 payload） │
                │   行宽 W，行数 R          │   │  cell 深度 D，位宽 B     │
                │   · 全并行比对            │──►│  · 按行号偏移取 payload  │
                │   · 只用于匹配，不存数据  │   │  · 下一跳/出接口/计数     │
                └──────────────────────────┘   └─────────────────────────┘
```

CAM 侧负责「快」：一次比对出所有命中行，按优先级取最高。SRAM 侧负责「大」：真正占容量的是这里。两者行号通过偏移映射绑定，所以**分配的复杂度几乎全在 SRAM 侧**。

## 2. 一条路由拆成什么

逻辑表项统一用三元组表示，与协议无关：

```python
Entry(key, key_len, payload)
# IPv4  /24  : key = 前 32 bit 有效, key_len = 24
# IPv6  /64  : key = 前 128 bit 有效, key_len = 64
# remote 模式: payload 多一段隧道信息，key 部分结构不变
```

把 IPv4 与 IPv6 归一成 `(key, key_len)` 之后，双栈不再需要两套表，只是 `key` 的比特宽度不同。远端模式只影响 payload，不进 key，因此不破坏匹配语义。

## 3. cell 位宽策略

一条路由占多少 cell，取决于 `key_len` 和位宽 `B`：

```
rows_needed = ceil(key_len_rounded / B) + ceil(payload_bits / B)
```

`key_len_rounded` 要把前缀长度向上取整到 CAM 行内可表达的最小单位（例如按 8 bit 对齐），否则短前缀无法在行内表示掩码。

三个位宽的实测差异（6000 条混合前缀：60% IPv4 /8~/24，40% IPv6 /32~/128，同等行预算，带 40% 插删 churn）：

| 位宽 B | 平均 span | 位利用率 | 同预算可装条目 | 碎片阻挡 |
|---|---|---|---|---|
| 32 bit | 2.71 | 0.851 | 2117 | 1490 |
| 48 bit | 2.44 | 0.625 | 2353 | 1429 |
| 64 bit | 2.22 | 0.515 | 2551 | 1394 |

三列指标指向三个不同的方向，**没有任何一档全面胜出**：

- **位利用率**随位宽上升而下降。总容量是「行数 × 位宽」，IPv4 /8 在 64 bit 行里只用了 8 位，剩下 56 位是纯浪费，这部分浪费是真实容量损失。
- **同预算可装条目**随位宽上升而增加。窄位宽一条长前缀要 4~5 行，宽位宽只要 2~3 行，行数才是硬约束时宽行赢。
- **碎片阻挡**（有足够空闲行但不连续，因而插不进去）窄位宽最多。span 越大的表项越挑连续空间，空洞一旦被打散，大表项先饿死。

所以选位宽的正确问法是：**当前硬件是行数先耗尽，还是总位数先耗尽？** 行数受限就选宽，面积/功耗受限就选窄，仲裁能力弱就避免 span 过大。复现：`python src/cell_allocator.py`。

## 4. 跨 cell 拼接：锚行机制

一条长前缀需要多行时，不能让匹配器把任意一行当独立表项，否则会出现「前缀只对上后半段」的脏命中。

```
逻辑表项 E (key_len = 128, B = 48)  →  3 行

row 0 : [VLD=1][锚][key 前 48 bit ][mask]      ← 只有这一行参与优先级仲裁
row 1 : [VLD=0][续][key 中 48 bit ]           ← 仅在锚行命中后按偏移连带校验
row 2 : [VLD=0][续][key 后 32 bit + 填充]
```

`VLD` 决定这一行是否为独立表项起点。匹配器只对 `VLD=1` 的行做仲裁，命中后按 `span` 字段连带读取后续行确认完整匹配。这样：

- 部分命中不可能被误判成成功
- 优先级排序只需要在锚行集合上做，比较次数从「总行数」降到「表项数」

## 5. 删除与碎片压缩

表项变长 ⇒ 删除必然留空洞。两种极端都不可取：

| 策略 | 问题 |
|---|---|
| 立即搬移填补 | 每次删除触发大量读写，删除风暴时流水阻塞 |
| 永不压缩 | 空洞尺寸不规整，大表项永远塞不进去，容量利用率断崖 |

采用**标记 + 阈值压缩**：

```
delete(e):
    mark e.rows as FREE
    fragmentation = free_cells / total_cells
    if fragmentation > HIGH_WATER:
        compact()          # 整段搬运，把尾部空洞收拢成连续区
```

`HIGH_WATER` 取 0.25 左右——低于它时零星空洞还能被小表项复用，高于它时连续大空洞几乎不可能自然形成，不压缩就会「总空闲很多但插不进一条 /128」。分配器用 best-fit 在空闲区里找，优先填尺寸最接近的洞。

## 6. 分配流水线

```
insert(key, key_len, payload)
   │
   ├─ 1. 归一化：把 v4/v6 映射到统一 key 空间，remote 模式标注 payload 类型
   ├─ 2. 去重：同 key + 同 key_len 已存在则覆盖 payload，不新增占用
   ├─ 3. 算需求：rows_needed(key_len, payload, B)
   ├─ 4. 找位：在空闲区 best-fit，找连续 rows_needed 行
   ├─ 5. 写入：首行置 VLD=1 并写 span，续行置 VLD=0
   └─ 6. 记账：更新占用位图、碎片率；越阈值则触发 compact

lookup(key)
   │
   ├─ 1. CAM 并行比对 → 得到所有 matched rows
   ├─ 2. 过滤 VLD=1 的行 → 候选表项集合
   ├─ 3. 按 key_len 降序取第一个（最长前缀优先）
   └─ 4. 按锚行 span 连带校验续行 → 返回 payload
```

第 3 步用 `key_len` 降序而不是「优先级字段」，是因为 LPM 的语义本身就要求最长前缀优先，硬件里通常等价为把长前缀放在更低的物理行号上——这一点在分配器里体现为「同族前缀按长度分桶，长前缀优先占低位」。

## 7. 边界与陷阱

实际踩过的坑，都写进了 `tests/test_sweep.py` 的用例：

- **前缀长度 0**（默认路由）：key 全 0、mask 全 0，`rows_needed` 计算容易和「空表项」混淆
- **/31、/32、/127、/128**：取整到行内单位时易溢出，`ceil` 边界写错会多算或少算一行
- **相邻前缀重叠**（/24 与 /25 同族）：删除 /24 时不能连带清掉 /25 的续行
- **远端模式与本地模式同 key**：两者 payload 不同但 key 相同，去重逻辑若只比 key 会互相覆盖
- **压缩过程中的中间态**：压缩不是原子的，扫描期间读到半搬移状态会误报，验证时需要停在压缩边界
