# 架构与分配策略

## 存储分层

```
                ┌──────────────────────────────────────────┐
   查找请求      │            LPM 查找流水                  │
   (dst addr) ──►│  key + mask 并行比对                      │
                └───────────────┬──────────────────────────┘
                                │ 命中的行号 (row index)
                                ▼
                ┌──────────────────────────┐   ┌─────────────────────────┐
                │   CAM 阵列（存 key/mask） │   │  SRAM 阵列（存 payload） │
                │   行宽 W，行数 R          │   │  cell 深度 D，位宽 B     │
                │   · 全并行比对            │──►│  · 按行号偏移取 payload  │
                │   · 只用于匹配，不存数据  │   │  · 下一跳/出接口/计数     │
                └──────────────────────────┘   └─────────────────────────┘
```

CAM 一次比对出所有命中行，按优先级取最高的一个。容量大头在 SRAM。两边的行号通过偏移绑定，
所以分配算法基本都作用在 SRAM 那边。

## 表项表示

统一用三元组，不带协议字段：

```python
Entry(key, key_len, payload)
# IPv4  /24   key 有效位 32，key_len = 24
# IPv6  /64   key 有效位 128，key_len = 64
# 远端模式     payload 多一段隧道信息，key 不变
```

IPv4 左移对齐到 128 位之后，双栈共用一张表，差别只在 `key_len`。远端模式只改 payload，
不进 key，匹配语义不变。

## cell 位宽

一条路由占多少行，由 `key_len` 和位宽 `B` 决定：

```
rows_needed = ceil(key_len_rounded / B) + ceil(payload_bits / B)
```

`key_len_rounded` 要向上取整到 CAM 行内能表达的最小单位（按 8 bit 对齐）。不取整的话，
短前缀的 mask 在行内表示不出来。

6000 条混合前缀（60% IPv4 /8~/24，40% IPv6 /32~/128），同等行预算，带 40% 插删：

| 位宽 B | 平均 span | 位利用率 | 同预算可装条目 | 碎片阻挡 |
|---|---|---|---|---|
| 32 bit | 2.71 | 0.851 | 2117 | 1490 |
| 48 bit | 2.44 | 0.625 | 2353 | 1429 |
| 64 bit | 2.22 | 0.515 | 2551 | 1394 |

位利用率随位宽上升而下降。总容量是行数乘位宽，IPv4 /8 放在 64 bit 行里只用了 8 位，
剩下 56 位是空占，这部分直接损失容量。

同预算可装条目随位宽上升而增加。窄位宽下一条长前缀要 4~5 行，宽位宽只要 2~3 行，
行数是硬约束时宽行占优。

碎片阻挡（剩余空闲行数够、但不连续，因而插不进去）窄位宽最多。span 越大越挑连续空间，
空洞被打散之后大表项先失败。

三列指标方向不一致，没有哪一档在三方面都占优。取值看硬件先耗尽哪一边：行数受限选宽，
面积或功耗受限选窄，仲裁能力弱就控制 span。复现：`python src/cell_allocator.py`。

## 多行拼接

长前缀要占多行时，不能把任意一行当作独立表项，否则会出现前缀只对上后半段的误命中。

```
逻辑表项 E (key_len = 128, B = 48)  →  3 行

row 0 : [VLD=1][锚][key 前 48 bit ][mask]      只有这一行参与优先级仲裁
row 1 : [VLD=0][续][key 中 48 bit ]            锚行命中后按偏移连带校验
row 2 : [VLD=0][续][key 后 32 bit + 填充]
```

`VLD` 标记这一行是否为表项起点。匹配器只在 `VLD=1` 的行里仲裁，命中后按 `span` 读后续行
确认完整。两个结果：

- 部分命中不会被判成成功
- 优先级比较只在表项数上做，不随总行数增长

## 删除与压缩

表项长度不固定，删除必然留空洞。两种做法各有问题：

| 做法 | 问题 |
|---|---|
| 立即搬移填补 | 每次删除都触发读写，删除密集时阻塞流水 |
| 不压缩 | 空洞尺寸不规整，大表项塞不进去，利用率下滑 |

实际用标记加阈值压缩：

```
delete(e):
    mark e.rows as FREE
    fragmentation = free_cells / total_cells
    if fragmentation > HIGH_WATER:
        compact()          # 整段搬运，把空洞收拢成连续区
```

`HIGH_WATER` 取 0.25 左右。低于这个值时零星空洞还能被小表项用掉；高于它，连续大块不会
自然形成，会出现空闲总量够但插不进一条 /128 的情况。分配用 best-fit，优先填尺寸最接近的洞。

## 分配流水线

```
insert(key, key_len, payload)
   │
   ├─ 1. 归一化：v4/v6 映射到统一 key 空间，远端模式标注 payload 类型
   ├─ 2. 去重：同 key 同 key_len 已存在则覆盖 payload，不新增占用
   ├─ 3. 算需求：rows_needed(key_len, payload, B)
   ├─ 4. 找位：空闲区 best-fit，找连续 rows_needed 行
   ├─ 5. 写入：首行置 VLD=1 并写 span，续行置 VLD=0
   └─ 6. 记账：更新占用位图与碎片率，过阈值触发 compact

lookup(key)
   │
   ├─ 1. CAM 并行比对，得到所有命中行
   ├─ 2. 过滤出 VLD=1 的行，作为候选表项
   ├─ 3. 按 key_len 降序取第一个
   └─ 4. 按锚行 span 校验续行，返回 payload
```

第 3 步用 `key_len` 而不是单独的优先级字段，因为 LPM 的语义本身就是最长前缀优先。硬件上
通常等价于把长前缀放在更低的行号，分配器里对应「同族前缀按长度分桶，长前缀优先占低位」。

## 边界情况

写进 `tests/test_sweep.py` 的用例：

- 前缀长度 0（默认路由）：key 和 mask 全 0，`rows_needed` 容易和空表项混淆
- /31、/32、/127、/128：取整时易溢出，`ceil` 边界写错会少算或多算一行
- 相邻前缀重叠（/24 与 /25 同族）：删 /24 时不能连带清掉 /25 的续行
- 远端与本地同 key：payload 不同但 key 相同，去重只比 key 会互相覆盖
- 压缩中间态：压缩不是原子的，扫描期间读到半搬移状态会误报，需要停在压缩边界
