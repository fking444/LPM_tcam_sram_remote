# 验证方法：地址扫描

## 1. 为什么不写「典型用例」

硬件表项的 bug 有个特点：**正常流量几乎碰不到**。日常转发打的是常规前缀、常规地址，而真正的错误集中在几个窄带上：

- 前缀长度取整的临界点（0/1、31/32、127/128）
- 相邻前缀重叠时删除顺序不同导致的状态残留
- 本地模式刚溢出到远端模式的那一条
- 碎片压缩进行到一半的中间态

用典型用例测，这些全都测不到，上线后在客户网络里炸。所以验证不用「挑几个好用例」，而是**按维度铺开扫描**。

## 2. 扫描维度

| 维度 | 取值 |
|---|---|
| 前缀长度（v4） | 0, 1, 8, 16, 24, 30, 31, 32 |
| 前缀长度（v6） | 0, 1, 32, 48, 64, 96, 122, 127, 128 |
| 地址形态 | 全 0、全 1、交替 `AA/55`、同族相邻、随机 |
| 模式 | 本地（不溢出）、远端（溢出） |
| 规模 | 单条、批量、接近满表、**超表**（预期报错，不能静默丢弃） |
| 操作序 | 纯插入、纯删除、插删交替、覆盖更新 |

完整组合会爆炸，实际做法是**两两组合 + 重点三维**：长度 × 形态全扫，模式 × 操作序只扫长度边界那几档。

## 3. 三层比对

单看「查表结果对不对」不够，出错了不知道是编码错还是查找错。分三层：

| 层级 | 比对内容 | 能定位的问题 |
|---|---|---|
| **L1 编码** | 下发后回读整表，与期望的 `(key, mask, payload)` 逐字段比 | 位打包错、大小端错、mask 生成错 |
| **L2 查找** | 扫描地址逐条 `lookup`，比 `命中前缀长度` 与 `下一跳` | 拼接不完整、优先级仲裁错、部分命中 |
| **L3 账目** | 占用 cell 数与分配器位图、碎片率自洽 | 泄漏、重复释放、空洞未回收 |

L1 挂了先修编码，L2 才有意义。跳过 L1 直接看 L2，会陷入「改了编码去迁就错误期望值」的坑。

## 4. 差分测试：期望值从哪来

期望值**不能**从被测实现自己推出来，否则是自证。参考实现独立写一份——朴素最长匹配，把所有前缀遍历一遍取最长的那个：

```python
def reference_lookup(prefixes, addr):
    best = None
    for p in prefixes:
        if (addr & p.mask) == p.masked_key:
            if best is None or p.key_len > best.key_len:
                best = p
    return best
```

O(n) 的笨办法，但**语义绝对正确**，作为基准。被测的硬件模型走 cell 分配 + 拼接 + 桶匹配。两者对不上，就是模型错了。

代价是慢，所以扫描规模控制在几百条、地址采样几千个，够暴露问题。

## 5. 失败输出要能直接定位

扫描挂掉时最忌讳只打印「结果不一致」。必须带全上下文：

```
FAIL len=127 pattern=ADJACENT addr=2001:db8::1ff
     expect: key_len=127 next=0x2a
     actual: key_len=122 next=0x2a
     rows:   锚行 r=18 span=3  续行 19,20
     hint:   长度取整边界，疑似 ceil 少算一行
```

有了 `前缀长度 + 地址形态 + 期望/实际 + 物理行号 + span`，基本一眼看出是取整算错、还是续行没绑上。

## 6. 两类已知误报

跑扫描时先用这两条排除掉，别当成 bug 追：

1. **压缩中间态**：触发阈值压缩后立刻读表，可能读到半搬移状态。验证时在压缩前后加同步点，或直接停掉自动压缩再测分配逻辑。
2. **写后立即读**：真实硬件有写延迟，行为模型是立即生效的，两者混用会出现假阳性。模型和真机要分开跑，别在同一轮断言里比较。
